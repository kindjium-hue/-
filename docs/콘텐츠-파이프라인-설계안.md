# 콘텐츠 제작 파이프라인 자동화 — 설계안

원고 한 편을 릴스 영상으로 만드는 과정을 **한 번의 명령**으로 줄이는 것이 목표입니다.
아직 코드는 쓰지 않았고, 이 문서는 검토용 설계안입니다.

## 1. 지금은 무엇이 수작업인가

현재 흐름은 `원고.md` → (사람이 대본 설계) → `make_reels.py`에 **파이썬 함수를 새로 작성** →
렌더 → 캡션은 별도 문서에서 복붙, 입니다. 구체적으로 걸리는 지점:

| 지점 | 현재 | 문제 |
| --- | --- | --- |
| 문구 | `s1_hook` ~ `s9_end` 함수 안에 하드코딩 | 자막 한 줄 고치려고 코드를 연다 |
| 타이밍 | `rise(t, 0.15, 0.6, 46)`처럼 상수가 코드 전역에 흩어짐 | 장면 길이를 바꾸면 안에 있는 beat 시각을 전부 다시 계산 |
| 장면 추가 | 함수 작성 + `SCENES` 리스트 수정 | 새 릴스 = 사실상 새 렌더러 |
| 검증 | 없음 | 자막 넘침·안전영역 이탈을 3분짜리 렌더를 다 돌린 뒤에 발견 |
| 크롭 | `draw_lib.CROP` + `assets/crop.json` 이중 | 어디가 우선인지 매번 확인 |
| 업로드 | 캡션·해시태그가 대본 문서에만 존재 | mp4·커버·캡션을 사람이 모아서 올림 |

핵심 진단은 하나입니다. **대본이 코드 안에 녹아 있어서, 대본을 바꾸는 일이 곧 개발이 됩니다.**

## 2. 방향 — 대본을 데이터로 꺼낸다

```
project.yaml (대본 = 단일 소스)
        │
        ├─ check    검증만. 몇 초.
        ├─ preview  대표 프레임 9장 contact sheet. 몇 초.
        └─ build    mp4 + cover.png + caption.txt. 몇 분.
```

렌더러는 "장면을 그리는 코드"에서 "대본을 해석하는 코드"로 역할이 바뀝니다.
새 릴스를 만들 때 파이썬을 여는 일은 **정말 새로운 연출이 필요할 때만** 생깁니다.

### 디렉터리

```
projects/<slug>/
  project.yaml        대본 + 메타 + 업로드 문구
  assets/             그 프로젝트 사진
out/<slug>/
  reels.mp4  cover.png  caption.txt  sheet.png
render/
  themes/topclass-dark.yaml   색·폰트·안전영역
  layouts/*.py                재사용 레이아웃
  draw_lib.py                 (기존 유지)
```

### project.yaml 스케치

```yaml
meta:
  title: 수학, 태도부터 바꿔 보세요
  size: [1080, 1920]
  fps: 30
  theme: topclass-dark
  cover_at: 1.9

assets:
  worksheet_a: { file: worksheet-a.jpg, crop: [0.03, 0.02, 0.60, 0.98], rotate: -90, boost: 1.15 }
  worksheet_b: { file: worksheet-b.jpg, crop: [0.27, 0.03, 0.87, 0.97], rotate: -90, boost: 1.20 }

scenes:
  - id: hook
    dur: 3.6
    layout: stack
    vo: 수학을 잘하고 싶다면, 문제집보다 태도부터 바꿔 보세요.
    beats:
      - { at: 0.15, y: 700,  style: sub, text: 수학을 잘하고 싶다면 }
      - { at: 0.55, y: 880,  style: h1,  text: 태도부터 }
      - { at: 0.80, y: 1030, style: h1,  text: 바꿔 보세요, color: mint,
          underline: { at: 1.35 } }
      - { at: 2.10, y: 1270, style: micro, text: 1년을 갈라놓은 건 머리가 아니었습니다 }

  - id: compare
    dur: 4.8
    layout: compare-cards
    cards:
      left:  { asset: worksheet_a, figure: upright, label: 매일 시도한 1년, tone: mint }
      right: { asset: worksheet_b, figure: slumped, label: 매일 미룬 1년,  tone: coral }
    beats:
      - { at: 0.10, y: 470, style: h2,  text: 여기 두 장의 학습지가 있습니다 }
      - { at: 0.90, y: 570, style: sub, text: 비슷한 수준에서 출발한 두 아이의 것입니다 }

publish:
  caption: |
    같은 수준에서 출발해, 같은 양을 풀고, 같은 수업을 들었습니다.
    ...
  hashtags: [수학공부법, 학습태도, 중등수학, 초등수학, 공부자극]
```

`vo:`는 지금은 대본 기록용입니다. 나중에 TTS 나레이션을 붙일 자리를 미리 비워 둔 것이고,
이번 범위에서 음성을 만들지는 않습니다(음악은 저작권 문제로 계속 인스타 라이브러리 사용).

### 레이아웃 5개로 기존 9장면이 덮인다

이 설계가 성립하는지가 여기서 갈립니다. 기존 대본을 분해해 보면:

| layout | 하는 일 | 커버하는 기존 장면 |
| --- | --- | --- |
| `stack` | 텍스트가 순서대로 떠오름, 밑줄·취소선 옵션 | 1 훅, 5 '수학 머리', 9 마무리 |
| `compare-cards` | 사진 2장 좌우 + 아래 손그림 + 라벨 칩 | 2 두 학습지, 8 결과 |
| `checklist` | 체크마크가 하나씩 그려지는 목록 | 3 같은 조건 |
| `divergence` | 한 점에서 두 선이 갈라지는 그래프 | 4 1년 뒤 |
| `quotes` | 인물 드로잉 + 대사 말풍선이 쌓임 | 6 해볼게요, 7 못 해요 |

9장면이 5개로 정리됩니다. 다음 릴스가 이 레이아웃 안에서 만들어지는 한 YAML만 쓰면 되고,
그렇지 않으면 `render/layouts/`에 하나를 더 추가합니다 — 그때의 비용은 지금과 같지만,
추가한 레이아웃은 그다음부터 재사용됩니다.

테마 파일(`themes/topclass-dark.yaml`)에는 색 팔레트, `h1/h2/sub/quote/micro` 폰트 크기 매핑,
안전영역(y 400~1560), 배경 격자·글로우, 상단 진행 바가 들어갑니다. 브랜드 톤을 바꿀 때
건드릴 파일이 한 개가 됩니다.

## 3. 자동화의 실제 이득은 `check`와 `preview`

`build`는 지금도 되는 일이라 크게 달라지지 않습니다. 시간을 실제로 아끼는 건 앞의 두 개입니다.

**`check` — 렌더 전에 잡는다** (실행 몇 초)

- 자막 폭이 좌우 안전 여백(80px)을 넘는지 — 실제 폰트로 `textlength` 측정
- `y`가 400~1560 밖으로 나가 인스타 UI에 가리는지
- beat의 `at + 애니메이션 시간`이 장면 `dur`을 넘는지 → **자막이 다 뜨기 전에 컷이 넘어가는 사고**
- 한 줄 16자 초과(모바일 가독성 기준)
- 총 길이가 릴스 한도(90초) 안인지, 훅 첫 문장이 3초 안에 끝나는지
- 에셋 파일 존재, 크롭 박스가 0~1 범위이고 좌<우·상<하인지

**`preview` — 장면당 대표 프레임 1장씩 붙인 contact sheet**

41.5초 × 30fps = 1245프레임 전체 렌더는 문구 한 줄 고칠 때마다 돌리기엔 너무 느립니다.
9장짜리 sheet.png를 몇 초 만에 뽑아 확인하고, 특정 시각만 보고 싶으면 `--at 12.3`.

## 4. 원고 → 대본 초안

`new <slug> --from script/원고.md`는 문단을 장면 후보로 쪼개고, 규칙으로 추정합니다.
따옴표 대사가 있는 문단은 `quotes`, "같은 A, 같은 B, 같은 C" 나열은 `checklist`,
짧은 단정문은 `stack`. 그리고 미채운 자리를 `TODO`로 남긴 project.yaml을 만듭니다.

**초안이 그대로 쓸 만할 거라 기대하지 않는 편이 맞습니다.** 목적은 빈 화면에서 시작하지 않는
것이고, 문구를 다듬고 강약을 정하는 판단은 사람(또는 Claude와의 대화)이 계속 합니다.
자동화의 몫은 그 판단을 **YAML 한 곳에 모아 두고, 틀린 곳을 즉시 알려 주는 것**까지입니다.

## 5. 이관과 안전망

기존 릴스를 첫 프로젝트(`projects/math-attitude/`)로 옮긴 뒤, 새 렌더러 출력과
지금의 `out/math-attitude-reels.mp4`를 **프레임 단위로 비교(PSNR)** 해서 리팩터링이 결과를
바꾸지 않았음을 확인합니다. 이게 통과해야 나머지 단계를 진행할 근거가 생깁니다.

## 6. 단계

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 1 | 테마·레이아웃 추출, `make_reels.py`를 레이아웃 호출로 재구성 | 기존 영상과 픽셀 동등 |
| 2 | YAML 스키마·로더, 기존 대본 이관 | `build`가 YAML만 읽고 같은 영상 생성 |
| 3 | `check` / `preview` CLI | 일부러 넣은 오류 6종을 모두 잡아냄 |
| 4 | `new --from`, `caption.txt` 번들 | 새 원고 한 편으로 처음부터 끝까지 통과 |

1~2단계까지만 해도 "자막 고치려고 파이썬 여는 일"은 사라집니다. 3단계가 시간을 가장 많이
아끼고, 4단계는 편의 기능에 가깝습니다. 도중에 멈춰도 각 단계가 그 자체로 쓸 만합니다.

## 7. 미리 말해 둘 한계

- **YAML은 코드보다 표현력이 낮습니다.** 아주 독창적인 연출은 결국 레이아웃 코드를 추가해야
  하고, 그 한 번은 지금보다 나아지지 않습니다. 다만 그 코드는 다음부터 재사용됩니다.
- **폰트는 나눔스퀘어라운드 시스템 경로 의존**입니다. 테마에 경로를 두되, 없으면 대체 폰트로
  조용히 바꾸지 않고 명확히 실패시키는 편이 낫습니다(글자가 깨진 영상이 더 나쁨).
- **오디오는 계속 없습니다.** 스키마에 `vo:` 자리만 남겨 둡니다.
- 사진 크롭은 `assets/crop.json`을 없애고 `project.yaml`의 `assets:`로 일원화합니다 —
  기존 crop.json을 쓰던 방식은 더 이상 동작하지 않습니다.
